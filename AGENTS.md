# Card development guidance

- Use PowerShell on this Windows workspace. Before a recursive delete or move, resolve and verify the absolute target, then use `-LiteralPath`.
- Ordinary new generals and skills that use existing capabilities change their content and registration. Existing shared loader, registry, and mechanism checks cover pure configuration. Add a focused behavior check only for behavior that is not already covered or for a bug fix; do not require a duplicate definition snapshot for each character. Do not raise the global rules epoch, skill JSON schema, or content package version per character. The content hash already distinguishes content changes during development.
- Optimize expansion for complete generals delivered per wall-clock hour. When parallel work is authorized, assign independent generals to agents and serialize only conflicting shared integration and final verification; do not default to assigning all agents to one general. Prefer existing capabilities and make a minimal implementation compile and exercise its main flow early.
- Do not require a fixed number of checks per general or repeat shared privacy, forged-input, collection-freezing, and replay checks at every character prompt. Keep focused checks for new behavior and actual regressions, with representative recovery coverage for new pending state. Defer speculative cross-skill and boundary combinations to a separate mechanism batch; pure content reuse does not need a new character fixture.
- Validate immutable skill definition shape in the loader, and reuse the executor's content-hash guard. Avoid repeating full static definition checks at each runtime continuation. Preserve dynamic payment, owner/frame identity, card movement, command validation, privacy, and save/replay contracts. Reuse stable integration and verification tools instead of creating a new family of scripts per general, and run routine verification once per integrated batch.
- Standing goal: a clean architecture where skills are compositions of rule concepts, each concept has one owner and one answer point, and a new skill needs only JSON. Follow the method in `docs/content/skill-composition/CAPABILITY_MAP.md`: when work hits a gap signal there (a character-specific or compound operation, a second implementation of a rule term, a character branch in a shared query), complete the missing concept with all its equivalent consumers instead of working around it, then lock it here and update the map. The user authorizes the best design and routine format migrations without repeated confirmation; preserve source saves when replay cannot continue, and document material behavior decisions.
- Before adding a character-specific `SkillProgramEffectOp`, `SkillProgramNumberExpression` value or condition kind, check whether an existing operation plus an effect-level `{"kind":"expression"}` condition expresses the rule (see `docs/content/skill-composition/RUNTIME_EXPRESSIONS.md`). A rule that only decides whether an existing operation runs must use the expression. When the expression lacks a read-only fact, add one shared read with its behavior check instead of a per-character operation.
- Skill upgrades, persistent upgrade flags, and skill grants/replacements reuse `Runtime/Rules/ProgramSkillChangeRuntime.cs` and the frame-aware helpers in `EngineOwners/CoreGameEngineProgramSkillChangesRuntime.ProgramSkillChanges.cs` through the existing program nodes. Keep rule-specific trigger, cost, and phase qualification outside the shared mutation layer; do not add a turn/round prerequisite to skill changes themselves. Keep paid child state and returns on the original frame. New generals that reuse these operations inherit the shared `Skill changes:` checks instead of copying an upgrade implementation or fixture.
- Do not add a global gameplay rules epoch or checkpoint `RulesVersion`. Replay saves under the current implementation with the existing schema, content and command validation; if the desktop cannot load or replay a save, initialize a fresh game without immediately overwriting the source save. Legacy skill JSON minimum-rules metadata is retained only for content fingerprint stability, never as a runtime gate. Raise `SkillProgramCatalog.RulesSchemaVersion` only for an incompatible rules JSON format; additive optional nodes can keep the existing schema. Change package versions for an intentional content release batch.
- Keep format version sources in `src/CardGame.Core/Replay.cs`, `src/CardGame.Core/SkillPrograms.cs`, and the relevant package's `CurrentVersion`. Do not copy current numbers into unrelated tests or development guides.
- Embedded rules omit the root rules version and load through `EmbeddedSkillProgramCatalog` with `SkillProgramCatalog.LoadCurrent`. External `Load` and Inspector validation still require an explicit supported rules version; do not add an optional-version fallback. Presentation and save formats keep their separate contracts.
- Test fixtures derive the current rules format from `SkillProgramCatalog.RulesSchemaVersion` or the shared fixture helper; keep numeric literals only when an intentionally incompatible format is the behavior under test. Batch incompatible rule-format retirements instead of bumping the format for each removed operation.
- Add focused Core behavior checks for the new rule. Add WPF checks only for UI behavior, and shared mechanism checks when a shared capability changes. Reuse the existing `--filter=<name>` runners and `tools/Test-Changed.ps1`; do not add character-specific runner switches or a new test framework. Run the relevant focused checks during development and routine verification after a batch.
- Full verification is manual only: run `tools/Test-Changed.ps1 -Full` or any unfiltered test runner only when the user explicitly requests a manual full run. Do not automatically start full verification after a change, batch, development milestone, or routine-check failure. This restriction remains in force throughout the main development cycle and later follow-up cycles until the user explicitly cancels it; completing the main development cycle does not lift it automatically.
- Preserve intentional test pruning when merging older branches or worktrees. Carry over only new checks for uncovered behavior or regressions; do not restore an entire historical test suite to match an old test count or branch convention. Resolve test conflicts against the current retained coverage and remove obsolete registrations, methods, and unused fixtures together. Do not prune checks in the same batch as a large refactor.
- Keep the default smoke checks near one second of test-process time; report build, dependency validation and runner overhead separately. Run relevant engine, replay, privacy, card movement and WPF regressions by existing name filters when those behaviors change. Prefer a small existing fixture or a verified seed over repeated seed searches and complete-match simulations. Retain integration coverage and all assertions for the behavior under test; measure the default run after a batch instead of assuming fewer checks means less time.
- Preserve checkpoint, replay, content fingerprint, input validation, privacy, and card movement boundaries. Do not delete historical compatibility code or change stored data solely to reduce test count.
- Invariants belong at shared boundaries: command validation, the loader, checkpoint restore and the executor. Character runtime code trusts the executor, frame cursor, typed child returns and payment receipts; it does not re-prove them with private events, history scans, `*Paid`/`*Proof` methods or `InvalidOperationException` sweeps. Do not record a private event for a fact the engine already records; read the existing record, adding one shared read if it is missing.
- Ordinary skill suppression, loss and borrowing use `skillState` / `ProgramSkillChangeRuntime`; `SkillAvailability` answers possession separately from effectiveness and `MatchSkillBindingIndex` only caches that answer. Invocation permission belongs to its actual window. Preserve and record distinct remaining lifetimes, continuous predicates and invocation-scoped rules in `CAPABILITY_MAP.md` while migrating them; do not extend legacy character-specific state stores or add another validity answer.
- Skill validity must be derived from declared data in one owner. Do not replace character qualification callbacks with a predicate registry, interface list or new callbacks. Store restrictions separately from real skill grants, use one matching function, and keep window-scoped invocation authorization separate from possession and effectiveness.
- Raw skill-source admission uses `SkillAvailability` for selection, reveal, identity concealment and immutable mode content limits; preserve possession separately from effective admission. Applied equipment-skill restrictions use the same recipient restriction table and metadata matcher, including future equipment grants; real equipment-effect and draw-penalty rules keep their own facts.
- Source-dependent skill grants use declared `skillGrants` conditions, exact `ConditionalSource` relations and `ConditionalSkillGrantRuntime`; `SkillAvailability` interprets their eligibility for both reads and synchronization. Retain independent grants and the original dependent instance across condition exits. Source-loss invocation permission stays on the original frame, separately from ongoing source eligibility; recipient restriction conditions must not recurse through source-dependent skill queries.
- Virtual Slash target eligibility uses `CoreNativeTargetLegalityRuntime.CanUseVirtualSlashTarget`; callers do not repeat its common SelfOnly, directed, effective-kind target bans or beneficiary-suit shields. Preserve source, material, distance, quota and rule-specific target requirements. Known suitless uses pass `Suit.None`; unknown suits remain null. Apply native appearance changes before this common decision; physical Slash and accepted-use continuation retain their own boundaries.
- Actual card-use history is derived from shared acceptance, native declaration, target-confirmation, finalization, role-update and completion facts through `IActualCardUseHistoryQueries`. Compose rule predicates and target sets with shared fact expressions; do not add per-character history predicates, collectors or proof ledgers. Preserve accepted versus confirmed/finalized/completed order, accepted declarer versus current actor, provider/responder identity, and the turn scope at each real sample. Keep latest targets, established-ever relations and window cutoffs distinct; real native uses without an Action must not acquire a fake ActionId. Freeze the history point and accepted qualification on the original frame for continuations instead of refreshing them from later nested history. Sequence rules compose accepted and immutable first-finalization views at the real window cutoff, without another pair ledger or a refreshed completion point.
- Actual-use occurrence reads preserve the original native declarer and declaration order, including their real response identity. Choose a completed-turn boundary explicitly when required; candidate-window and current-time cutoffs remain separate. Do not count accepted-only attempts as declared uses or silently widen self-supplied responses to other response origins.
- Card-use confirmation expressions read each real confirmation separately: the confirmation view retains the raw event targets, while latest/observations retain designated targets. Confirmed targets, normalized primary targets and sampled phase survive ordinary role/target updates as last-confirmation metadata; confirmation does not imply finalized/Established. Match declared kinds through the shared card-kind matcher, preserve unknown reads and real identity comparisons, and choose live qualification versus a frozen boundary cutoff explicitly.
- Actual phase history uses the original phase-start facts and shared actual-skip facts through `IActualPhaseHistoryQueries` and `phaseCount`. Restoring a phase is not a new entry; skip requests, substitutions and skill payments are not actual skips. Preserve natural, inserted and extra-draw occurrences, actor/turn scope and journal cutoffs; keep distinct cost facts where a rule counts payment rather than outcomes.
- Delivered native Draw and awaited bound-gift instructions use the original frame's instruction delivery to drain their own children and finish their terminal instruction after source loss or death. Keep delivery on the original frame, including zero-card or legally replaced results; delivery never authorizes an unpaid suffix or an undelivered request. Preserve the synchronous path's existing contract when no native producer is used.
- Target card-use quotas use `IProgramTargetQuotaQueries` for the aggregate answer, including general allowances that also permit Slash. Issue independent allowances through directed-policy data; keep native recipient slots on the original instruction and keep quota permission separate from actual use history.
- Directed card-use rights use the shared directed-policy data and boundary lifetime owner. Declare continuing source eligibility separately from an applied right and its accepted-use snapshot. Capture on the original declaration, payment and use before lifecycle consumers; do not rebuild character leases or private proof events. Keep all-use quota exemptions distinct from Slash-only quota exemptions.
- Assisted native Slash requests declare invocation authorization on their original frame at issuance. Shared target and payment queries consume the explicit request and its authorization instead of character-origin whitelists or an unrelated active request; preserve live material and range rules, original payment, and typed returns.
- Faction-supplied Slash target eligibility uses `IProvidedSlashPaymentTargets`; do not gate actual-material validation on a character or distance/color privilege. Candidate conversion and final-kind issuance query the same actual materials separately.
- Native zero-entity attacks with the standard completion protocol declare that role on their original `CardUseFrame` at issuance; `CoreNativeSlashCompletionRuntime` owns their completion window and existing typed return. Do not add per-character completion hooks for that same protocol. Keep group-card iteration, material retirement and rule-specific post-use progression in their actual owners.
- Follow a real card-use resolution chain to identify reusable facts, conditions, trigger windows and effects. Keep actual use/response facts separate from quota accounting, and keep nested resolution on owning frames; a Slash example is a path through common rules, not a separate family of skill implementations.
- Fixed effects already issued for a card use use `CardUseFrame.CardDamageAdjustments` and `CoreGameEngineCardUseLifecycleRuntime`; current-occurrence damage changes stay on the actual damage attempt. Preserve whole-use versus target scope and card-damage versus additional-damage layers. Do not rebuild character boost ledgers or requalify paid effects when their source disappears.
- Issued target response requirements use the actual incoming frame's `ResponseRules` and the shared Lifecycle query; direct program uses retain their original instruction scope. Distinguish the card actor, current opponent, logical responder and material provider. Minimum requirements combine by max and prohibitions by OR. Never find a response rule by searching for a character-marked ancestor; keep current-attack cancellation, counter-Nullification and dying rescue boundaries distinct.
- Whole-use response prohibitions share that same rule data with an explicit audience, including non-target responders and both Duel directions. Source attribution supports explicit withdrawal of that source's applied policy; source loss or death does not itself withdraw issued rules. Native compound instructions return to the original program cursor so ordinary JSON steps can consume their declared outputs.
- Permanent physical card marks use `CardEntityMarkRuntime`, `markInitialHand` / `markCards`, and the shared `cardMarkCount` read; keep mark identity independent of holder, zone, source skill and presentation label. Holder-dependent benefits remain separate rules. Printed Lord qualification belongs to the actual grant as typed setup/program source data and uses the single `PrintedLordSkillQualifications` matcher.
- Generated equipment uses `EquipmentCardOrigin` and `EquipmentDestinationPolicy` through `GeneratedEquipmentRuntime`; random pile selection, private generation offers and native placement reuse the equipment composition nodes. Equipment's own entry/departure triggers declare `ownEquipmentOnly`; departing sources freeze before movement and reuse `ProgramInvocationAuthorization` on the owning movement window, never a replacement skill grant or character ledger.
- Applied states outlive their caster and original skill. After application, evaluate the recipient's declared conditions, lifetime and removal rules; do not revoke a state merely because its caster died or lost the skill. Source qualification controls new applications and future windows; it does not requalify an already applied state. Read HP through the existing match health query, including its mode conversions and selected health receipts.
- Accepted card-action and movement trigger continuations use `ProgramInvocations` on the original native window and candidate cursor. Acceptance-scoped rights begin only after the actual binding starts; preserve earlier source-frozen permissions as distinct declarations. Keep source-loss invocation rights separate from owner-death rights; never refresh accepted qualification from later use history or recreate character payment-proof ledgers.
- Passing checks prove behavior, not design. Judge a change by the clean-architecture criteria in `docs/content/skill-composition/CAPABILITY_MAP.md`; line and operation counts are symptoms, not goals, and adding code is right when it makes the design cleaner. Moving code between classes or generating adapters is not simplification.
- Keep `CAPABILITY_MAP.md` focused on concept ownership, completion, rule semantics and remaining gaps. Put batch timings, size statistics and detailed verification results in commit messages, not the capability map.
- Accepted materials are commitments on their original frame, separately from chosen inputs and physical payment results. Acceptance freezes eligibility; execution drops materials that left their frozen source without requalifying the promise. Declare source-loss continuation separately from owner-death draining, and never use draining to issue future effects.
- Public Hand reveal producers use `IPublicHandRevealWindows` for issued candidates, suspension and returns. Keep source qualification outside that shared owner, consume issued candidates by the original frame cursor, and return to each producer's actual owner. Do not prove window progress by scanning character events; declare source-loss and owner-death invocation permissions separately.
- Public show sources use the existing canonical reveal events and `IPublicCardRevealQueries`; hand residency uses `ICurrentHandEntryQueries` over the physical movement journal. Keep reveal occurrences, remembered visibility during one hand entry and skill-specific quotas distinct. Character rules retain their actual sampling times and do not rebuild source switches or borrow another character's frame-proof helpers.
- Public show history uses `IPublicCardRevealHistoryQueries` over shared native samples. Capture only source facts missing from the original reveal event; rules retain their actual residency, phase, turn and material-disclosure semantics instead of rebuilding character event ledgers.
- Expression card sets carry only known frozen facts and original physical residency. Derived bindings inherit source locations and entry tokens, including unknown tokens, rather than sampling a new origin; use the shared zone-entry query. Accepted after-turn-ended calls retain only their declared original-frame invocation permission, independently of owner-death draining.
- Trigger usage keys and consumption use `ProgramTriggerUsageRuntime` / `ProgramTriggerUsageRules` over the existing skill store and native Event window. Issued opportunities reserve declared limits once and retain that reservation on the original invocation; beginning the binding does not pay it again. Freeze qualification facts privately on the owning frame, keep source loss and owner death independent, and identify native activation sources from actual activations rather than unrelated reward triggers.
- Dependency direction: shared modules depend on shared capabilities; character implementations depend on shared capabilities and do not depend on other character implementations. Entries and per-target injection are transitional wiring, not capability boundaries. Do not hide reverse dependencies in large context objects, service locators or generic query interfaces, and do not optimize constructor length independently of removing reverse dependencies.
- Declare native fact demand at the capability definition; shared capture must not enumerate character capability flags. Keep trigger and activation demand distinct. Compile operation/passive declarations, generic traits, expressions, windows and skill-state Until requirements, including declaration State.Until. Compose immutable catalog facts with the selected mode RequiredFacts in the match provider, never by mutating the shared catalog. Shared capture gates read the same match INativeFactDemand mask; ActualPhaseEnd implies actual-phase identity, and both mode contracts and compiled masks reject unknown requirements.
- Fact demand gates capture, not rule qualification or observer scheduling. Preserve specialized capture, OwnedDraw producer admission and actual-skip timing; a mode phase requirement must not create extra DrawSkipped observer frames. Keep issued phase-end collectors and typed single-candidate returns explicit until their rules are actually declared; removing demand branches does not complete that execution concept.
- Keep logical acquisition collections separate from physical movement batches. Freeze acquired entities, original-hand witnesses and each required source time in shared receipts on the owning batch; characters consume those facts instead of rebuilding them with completion callbacks or private history. Typed replacement provenance stays at its native boundary, and acquisition grouping must not merge or discard ordinary movement windows. Captured invocation permission belongs to its original window and program, independently of skill possession and effectiveness; source-loss permission must not implicitly grant owner-death permission. Read-only card captures do not acquire temporary-material cleanup ownership; derived bindings preserve that ownership and private reads stay within their authorized participant scope. Read movement outcomes from original physical facts, separately from requested materials and logical discard semantics.
- The existing runtime-composition check locks current constructor-direction violations to an exact baseline: new violations fail, and removed violations require deleting their baseline entries. A passing legacy baseline does not complete a concept. From the use/response legality batches onward, completion also requires the concept's shared modules to have no concrete character dependencies.

## Temporary files and build artifacts

- Benchmark logs, verification summaries, screenshots, source snapshots, and recovery archives are temporary outputs. Use the ignored `.artifacts/benchmarks/` directory when they need a repository-local location; do not add them to Git or maintain references to them in documentation or source manifests. Keep lasting rule explanations and source citations in the relevant documentation instead.
- Generate release/publish outputs, installers, and distribution packages only when the user explicitly requests publishing or packaging. Ordinary development and verification must not run release/publish workflows. This restriction does not prohibit temporary archives used to complete the task.
- Temporary archives, repository/asset copies, worktrees, and isolated build/test outputs are allowed when useful; no separate permission is needed just to use them. Track exact paths and ownership. Reuse compatible checkouts and build outputs, respecting locks and concurrent work, instead of creating a new timestamp/GUID directory for each feature.
- Automatically clean up this task's disposable temporary files and directories as soon as their purpose is complete, including `%TEMP%` diagnostics, isolated `.artifacts` build/test outputs, temporary archives, and small test fixtures. This standing instruction authorizes ordinary task-owned cleanup without another confirmation. Preserve deliverables, necessary diagnostic evidence, recovery backups, and outputs the user explicitly requested to keep before cleanup.
- Before recursive deletion, resolve and verify the exact absolute target is strictly inside the intended temporary/output root, check ownership, reject linked paths, and stop or wait for this task's own consumers. Respect verification locks and concurrent work. Use PowerShell cmdlets with `-LiteralPath`; never clear all of `%TEMP%`, delete by a broad `Card-*` wildcard, or delete another task's outputs/shared caches.
- Put automatic cleanup in `try/finally` where practical, covering successful and failed runs. Before the final response, verify that disposable outputs were removed. When resuming an interrupted task, inspect its known temporary paths and finish any permitted cleanup. Registering a path does not mean space has been freed.
- If cleanup is rejected as `blocked by policy`, do not retry the same deletion through a script, another tool, or a later task stage to bypass the rejection. If policy, permissions, locks, or necessary diagnostic retention prevent cleanup, register the exact retained directory with `python -B tools/cleanup_temp.py --add <absolute-directory> --root <verified-temporary-or-output-root> --reason <reason>`; include `--lock-root <artifacts-root>` for verification outputs. Report its path and reason in the final response.
- `tools/cleanup_queue.json` is the fallback UTF-8 text database for retained directories. Inspect it with `--list`/`--dry-run`; the user can double-click root `clean.cmd` or run `python tools/cleanup_temp.py` to retry cleanup. Agents must not run the entire historical queue automatically or use it to retry policy-blocked deletion. Remove only the matching records after successful deletion or verified absence, preserve unrelated entries, and retain failures for retry.
- Prefer the stable default directory of `tools/Test-Changed.ps1` and reuse its outputs during the task. The runner currently registers its `bin`, `obj`, and `renders` and retains them; this does not discharge the agent's cleanup responsibility. Once verification and inspection are complete, automatically remove this task's disposable outputs when permitted, preserving necessary summary/logs. Explicit `-ArtifactsPath` follows the same lifecycle; honor explicit user requests to retain outputs.
- Cleanup tests may mock deletion and must not remove real historical queued directories. Automatically clean up their own disposable fixture directories after testing when permitted; register them if cleanup is blocked.

## Runtime boundaries

- Keep command commit and recovery in the command session. Prepare player views before commit; freeze all exposed nested collections so observers cannot change the prepared result. Player views must use `CreateSnapshot(viewerSeat)`; `ResolutionStack` is trusted diagnostics and may contain private state.
- Freeze collection-bearing event payloads in commit preparation before they enter history or reach observers. A read-only record does not freeze its lists or nested policy/deposit objects; new built-in event collections must be covered by `CommittedEventProjection`.
- Keep pending resolution state on its owning frame. Use runtime push/replace/complete methods and typed parent returns; do not add parallel pending objects or use-ID sidecars for migrated state. A resumed child must not pay a completed cost twice.
- Native Give facts belong to `NativeGivenCardRuntime` and the original journal, with scope interpreted by `NativeGiveScopeRuntime`. Declare logical giving and its actor in rule data; do not infer Give from movement zones, reason strings, gains or a character whitelist. Logical Give triggers declare perNativeGive on the original movement window; keep logical occurrences separate from physical completion indexes and derive capture demand from the declaration. Typed gain settlements keep their original producer contract; do not rebuild character ledgers or re-prove replacement issuance when reading delivered facts.
- Exact owned-card movement requests reuse the original OwnedCardSelection draft and typed SelectedCardPayment. Issue one request only after a full legal selection; distinguish accepted selection from actual delivery, including redirected, destroyed and retained outcomes. History-based card identities do not grant private face access or temporary-material cleanup ownership.
- Native multi-stage instructions reuse `ProgramStageRuntime`: declare the next stage before issuing a paid child, reread the original receipt after draining children, and keep dynamic termination rules in the recipe. Ordered random acquisition from other seats uses `ProgramRandomSeatAcquisitionRuntime`; version policies retain selection priority, turnover rules and event projection without repeating the movement loop or scanning history to prove completed payments.
- New rule events must use `AdvanceEventRulesAndQueueFact`; new state progression must use `AdvanceRulesAndPublishState`. `QueueGameEvent` and `PublishState` are output-only helpers and must not become rule entry points again.
- Run `tools/Test-Changed.ps1` without filters for the measured routine scope in `tools/VerificationScopes.psd1` and relevant name filters while developing. Full verification follows the manual-only restriction above. Routine coverage and all registered checks are different scopes; report actual timings and failures. Fix each failing check you see or confirm it already fails on the base commit; only an explicit user request starts full verification.
