## 龙卫：可确认内容与未公开部分

14101龙卫主文为：“出牌阶段限一次，召唤1个随从，若有随从已阵亡，则改为将其复活，并令其摸牌至5”。主文明确了本人出牌阶段限一次、一名随从、存在阵亡随从时改走复活，以及复活分支的补牌至五。它没有公开多个可选对象的选择顺序、复活体力与状态、首次召唤时的起手处理，或首次召唤是否也补至五。

同版 Client 将 `LongWei2` 注册到 `HSi`，该类完整实现只有：

```javascript
class HSi extends BJt {
  constructor() {
    super();
    this.activeMode = Nmt.ACTIVE;
  }
}
```

这能确认它使用主动技能客户端入口；类中没有召唤席位、阵亡对象筛选、体力、补牌或入场实现，不能拿一个空客户端壳当作服务器算法证据。

两名隐藏京畿募兵与两名初始可见京畿募兵共同构成校尉身边的四个原随从身体，是后续实现应保存的固定来源名单；不得据“召唤”无限追加新角色，也不得把任意同队角色当作已证实的原随从。**两名隐藏身体是否确实按首末顺序启用、多个原随从阵亡时谁复活，以及是否还存在其他服务端筛选条件，当前材料不能确认。**“用两名隐藏预留席承载新召唤、从原四名随从选择复活”与原配置相符，但目前只是有依据的实现方向，尚不是已经确认的完整服务器规则。

若后续采用预留席，必须分别表达未入场、已入场存活、已入场阵亡；不能把“未入场”和“已死亡”混为一个布尔状态。原文本的“有阵亡随从则改为复活”也不能在尚有隐藏席时擅自绕过。完整固定敌军身体占五席，八人上限下连同玩家最多再容纳两名同伴，不能只按可见三敌选满同伴后再把两名随从塞入超额新席。

## 其余三项能力

**965募兵**可准确复用 `ol:mubing`。主字段 `o` 是出牌阶段开始时可选亮出三张，再弃任意手牌，以弃置点数和不少于获得点数和换取亮出的原实体。既有 `src/Characters/zhang-liao/ol-sp/Skills/ol-sp-zhang-liao.rules.json` 与 `Runtime/GameEngine.SpZhangLiao.cs` 已有原生展示、付款、取得和孩子返回；按真实技能实例工作，没有原张辽人物身份门槛。来源 `ap` 是四张并可分配的升级文字；本组没有授予调令，因此不得把这段升级文字直接当成965的基础规则，也不附带自取或调令。

**360抚蛮**可准确复用 `ol:fuman`。其 `ordinary-ma-zhong.rules.json` 和 `GameEngine.GiftedSlashUseRewards.cs` 已包含每个实际出牌阶段每名其他目标限一次、交给一张真实手牌、该原实体在受赠者连续手牌持有期间视为杀、实际使用后按是否造成伤害由原授予者摸一或二张。这里不是给随从授予一个“抚蛮”技能，也不是把“杀牌”凭空复制给对方；不改用只能赠送原杀且有下回合期限的移动版抚蛮。

**1606帅令**主文为：“锁定技，友方角色的摸牌阶段开始时，其判定，若结果为黑色，其获得此判定牌。”本组只把它授给21档校尉，由校尉观察实际友方摸牌阶段；不是给每名随从印刷同一技能，也不是让校尉代领友方判定牌。当前源码没有完整同名能力。已有 `startJudgment`、最终花色过滤、真实判定牌转移等节点可复用，但跨友方真实摸牌开始的资格与父窗口仍须接入：`SkillPrograms.cs` 对其他角色或任意角色 `drawPhaseStarting` 只准已有审核过的专用入口，不能拼一个任意 JSON 触发器越过限制。新增入口应保留校尉技能来源、实际友方摸牌者和真实摸牌父帧，并把黑色最终判定原牌交给该摸牌者；不以摸牌结束或获牌窗口近似。

## 当前框架缺口与接点

`StandardShanheCampaignCatalog.Source2026.EnemyData.cs` 中 `Source2026EnemyData.Hidden` 仅用于计算 `SourceVisibleEnemyCount`，`ApplySource2026EnemyData` 没有把隐藏或未入场状态传入战斗成员。`ShanheCombatantDefinition` 当前也没有隐藏预留、未出生或原随从归属字段。`ActivityPlayerSetup.BuildCampaignPlayers` 会遍历整个 `EnemyRoster`，将每一行建立为已经选择并公开将领、正体力的真实角色。因此只保留原五行再设置可见计数，仍会实际开出五名已入场敌人；只保留三行则又丢失两个预留身体，二者都不是完整实现。

后续需补的内容边界是固定原成员身份与初始生命周期、开局发牌及轮次资格、入场后真实技能与事件、胜负判定，以及14101拥有帧上的一次主动发动和明确的实际入场或复活子返回。现有 `GameEngine.ShanheMulu.cs` 的 `RestoreProgramCharacterLife`、复原事件和孩子返回可作为已入场死者复活的参考；木鹿规则本身却是本人回合开始自动复活所有指定大象，没有隐藏预留席，也没有龙卫主动召一、阵亡优先或补手至五，不能直接挂上木鹿召唤当作已实现。

本预审不新增枚举、角色包、共享入口或测试，也不提出假定的产品规则来掩盖上述缺口。
