# 基础能力：方法与地图

技能应当是规则概念的组合。前半部分是发现、判断和补齐基础能力的方法，后半部分是当前地图，由执行者在每次补齐后更新。

## 干净的架构是什么样

判断架构是否干净，靠读代码回答下面这些问题，而不是看行数或指令数：

- **一个概念，一个归属**：每个规则概念（技能有效性、使用合法性、获得、交给、距离……）只有一个拥有者。“这个技能现在有效吗”“这张牌能用吗”这类问题，在引擎中只有一个地方回答。
- **依赖方向单一**：规则概念不知道具体武将；武将依赖概念，武将之间互不调用。共享查询里没有人物分支。
- **层次分明**：每条规则落在它该在的层——触发时机、效果步骤、持续规则（修正 / 查询）、流程（顺序、分支、逐个结算）。“此次伤害 +1”是修正，不是伤害步骤；“不能使用”是查询，不是执行动作。
- **技能读起来像规则原文**：对照一个技能的描述，可以在它的 JSON 中逐句找到对应的部分，没有为了凑合实现而多出来的步骤，也没有藏在 C# 里的半句规则。
- **改动是局部的**：改一个概念时不用碰技能；加一个技能时不用碰引擎或其他技能；新老技能的交互由概念保证，而不是靠彼此打补丁。
- **只有一条路径**：同一件事没有新旧两套实现并存，也没有为过渡留下的适配层。
- **信任边界清楚**：校验只放在边界（命令输入、加载、存档恢复、执行器），内部代码互相信任，不重复自证。

看代码增长落在哪里：概念层（共享能力、查询、层次之间的接口）的代码随概念增加而增加，补齐后趋于稳定，这是健康的；随武将数量线性增长的专属代码、适配层、转发和自证，是不健康的。正常迭代中，前者可以放心增加，后者应当趋近于零。

行数和指令数只是表现，不是目标。多数情况下，架构变干净后体积会变小；但如果增加代码能让结构更干净，例如补一个完整的概念、明确一个回答点、拆开一个焊在一起的指令，就应该增加。

## 发现缺口的信号

在日常开发中遇到下面任一情况，就说明有基础能力缺失，应停下来对照本文，而不是绕过去：

- 准备新增的指令名里含有武将名、技能名，或含 Then / And / Or / If / When。
- 同一个规则术语已经有两个以上专属指令或专属实现。
- 一个共享查询里出现了针对某个人物的分支。
- 回答同一个“能不能 / 是不是”的问题，需要查看多个地方。
- 为了让新技能和老技能正确交互，需要修改老技能的代码。
- 写 JSON 时必须借助一个只服务本技能的 C# 指令，否则无法表达。

## 判断：封装、组合还是保留

- **封装成基础能力**：规则里有术语的概念（失效、获得、交给、视为、限制使用、觉醒……）；引擎需要在一处回答的问题；会与其他技能交互的状态。即使目前只有一个武将使用，也应封装。
- **用组合表达**：“先 A 再 B”、按结果分支、按条件执行，用 JSON 步骤序列和 `expression` 条件表达。即使很多武将都这样写，也不封装成新指令。
- **保留 C#**：单个武将独有、与其他规则没有交互的特殊流程。不为了消除它而去造一个只有它会用的“通用”能力。

使用次数只用来发现问题（同一概念出现多种写法），不作为是否封装的依据。

## 补齐一个概念的步骤

1. **普查**：在 JSON 和 C# 中找出这个概念的全部用法，整理出它在规则上的维度（动作、对象、范围、持续、例外），以及它与其他概念的交互（例如锁定技不受失效影响）。
2. **定义**：确定最小的参数集合、唯一的回答点，以及它分别落在哪一层：效果步骤、持续规则（modifier / 查询）还是触发窗口。参照已有的同类能力，复用现有存储和协议，不另建体系。
3. **实现并迁移**：在同一批中实现能力，并迁移所有能等价表达的消费者；删除旧的专属指令、分散判断和人物分支，不留两套实现。有规则差异的保留原实现，在本文记一行原因。
4. **锁定**：在 AGENTS.md 中用一句话写明“该概念统一使用这个能力”，并更新本文地图中的状态。
5. **自检**：完成前用“干净的架构是什么样”逐条检查这个概念：
   - 一个用到它的新武将，能否不写 C#？
   - 引擎中是否还有第二个地方在回答同一个问题？
   - 迁移后的技能是否能与规则原文逐句对应？
   - 是否还残留旧路径、适配层或人物分支？

   任何一条不满足，就继续完善，或者在本文说明原因。

## 选择下一个概念

优先处理离“干净”最远、交互面最大的概念：同一概念的写法越多，被其他规则查询得越频繁，就越优先。每完成一个概念后重新评估顺序。日常新增武将时发现的缺口，记入地图，按同样的标准排队。

只有下列情况需要用户决定：规则解释存在分歧；需要改变存档、回放或命令格式；迁移会改变已有技能的实际行为。

## 缺失项的证据

- **技能状态**：初始普查发现共享查询直接调用刻铭、各失效判断分散。当前普通回合失效、断肠已迁共享状态并删除两个 Admit 证明钩子；刻铭、引祉、砺誓等不同规则仍有专属判断，整体尚未完成。
- **使用合法性**：`IsSlashProhibited`、`IsCardTargetProhibited`、`IsBlackTrickTargetProhibited`、`ShanheS5TongjiProhibitsSlashTarget`、`ShenwuRobeDirectedTargetProhibited` 等按武将或卡牌各自实现。新增一个“不能使用”“不能成为目标”的技能时，需要找到所有相关入口。
- **获得 / 交给**：例如 `obtainOneFromEachSelectedTarget`、`revealHandColorDiscardAndTake`、`giveAllHandAndStartRecipientPindian`、`revealHandGiftAndResolveRecipientChoice`，大多是“获得 / 交给 + 其他步骤”的组合。
- **觉醒 / 限定技**：如 `awakenOlTianxing`、`awakenJianghuo`、`awakenHappyTaishiCiPowei`。每个觉醒技都单独写了检查、标记和后续变化。

## 当前建议顺序

基于本次盘点，按缺口大小和交互面排序，执行者可在普查后调整：

1. **技能状态**：一个动作（失效 / 失去 / 夺取 × 对象 × 范围 × 持续），一个持续规则（条件期间失效），一个“技能是否有效”查询；移除 `HasRuntimeSkill` 中的人物分支。
2. **使用与响应合法性**：一个“能否使用 / 能否指定 / 能否响应”查询，由 modifier 声明限制；现有 `grantTurn*Prohibition` 改为写入同一来源。
3. **获得 / 交给**：统一来源区域、选择者、可见性和数量，拆掉“获得 + X”的组合指令。
4. **觉醒 / 限定技**：统一的觉醒条件（表达式）、已发动状态和后续技能变化（复用技能变更）。
5. **无效 / 取消目标**、**装备**、**弃置参数化**、**伤害修正**。


## 技能状态：2026-11-01 迁移进度

### 归属与维度

- 存储复用来源明确的 `CharacterSkillSet`；限制与获得来源一同随 revision 失效缓存，不新增 pending 或独立状态机。
- `SkillAvailability` 区分 **持有** 与 **有效**；`MatchSkillBindingIndex` 缓存回答并构建绑定。调用是否允许仍由实际触发窗口、次数、支付和目标资格回答，不能用持有代替。
- `skillState` 的动作是 `suppress`（仍持有但失效）、`lose`（失去当前来源）、`transfer`（借出方失效、施术方获得独立来源）。后者不表示永久夺走；实际失去并获得应分别表达两个动作。
- 范围为 `all / nonLocked / named / chosenFromTarget / expression`，可限定 `printedOnly`、`excludeLocked`；`characterOnly` 默认 true，显式 false 才覆盖装备来源，模式规则始终保护。
- 期限为本回合、指定角色最近一次回合结束、永久。`untilTurnEndOf` 默认包含当前回合；`afterCurrentTurn:true` 才排除发出时的回合。`expireOnDeath:true` 另以受影响目标（借出方）死亡为结束条件，不与回合结束座位混用。
- 失效覆盖匹配的现在和未来来源；暂时失去只限制当时的 grant，结束时移除限制，不能恢复永久失去的 grant 或删除后来独立获得的来源。永久失去直接禁用当前来源，不保留将来一切同名技能都失去的通配限制。
- 借用复用已持有的实例、boolean 状态和次数，不重复发获得事件；到期只移除本来源。
- 本回合期限沿用实际回合清理位置，在归还扣押牌可能打开移动子结算之前解除。指定角色回合末/死亡期限走各自事件边界；不能只因期限名字相同就改变 BeforeEvent/AfterEvent 顺序。
- 技能筛选复用 expression；`number` 的 `skill.locked / limited / awakening / lord / printed / ordinal` 是本次候选技能的内建事实。普通 number 和牌绑定仍走原资源检查；筛选结果在本步确定，不成为持续条件光环。
- 选择挂在原帧，按 chooser 的 `CreateSnapshot` 限制候选并使用私有 prompt；服务器仍校验回答，续接执行原指令后面的普通步骤。冷恢复继续接受命令重放，不增加存档版本门槛。
